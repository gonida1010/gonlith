## 1. 한국어·영어 어휘 검색 비교

평가셋 `memory_retrieval_ko_en_v1`: 가상 인물에 대한 기억 50개, 질의 60개.

| 영어 | 12 |

**유형별 R@5:**

| 유형 | 2-gram | kiwi | trigram |
| :--- | :--- | :--- | :--- |
| 2글자 단어 | 1.000 | 1.000 | 0.385 |
| 조사 변화 | 1.000 | 1.000 | 0.625 |
| 어미 활용 | 1.000 | 1.000 | 0.000 |
| 동의어 | 0.333 | 0.667 | 0.333 |
| 영어 | 0.917 | 0.917 | 1.000 |

**2-gram이 놓친 질의 (k=5):**

| 질의 | 정답 기억 | 성격 |
| :--- | :--- | :--- |
| "어디 살아?" | "…마포구에 산다" | 활용형 원형 복원 필요. kiwi는 찾음 |
| "알레르기" | "allergic to cats" | 한·영 교차 |
| "cat allergy" | "allergic to cats" | 영어 어형 변화 |
| "log retention" | "Logs are kept for 30 days…" | 동의어 |

**결론 (판단):**
* 기본 토크나이저는 2-gram이다. 기준선 대비 R@5가 +0.367이다.
* kiwi는 60개 질의 중 1개를 더 찾는다(+0.016). 대신 설치가 약 126 MB 늘고 첫 로딩이 816 ms 걸린다. 그래서 선택 설치(`gonlith[korean]`, 설정 `search.tokenizer = "kiwi"`)로 둔다.
* 남은 오답 3개는 의미 검색이 필요한 유형이라 S7(임베딩)의 기준선으로 쓴다.
* `search.default_limit`: 이 평가셋에서는 R@5 = R@10이었다. 공개 데이터에서는 R@10이 더 높아 최종값은 10이다(§1b).

**한계:**
* 평가셋은 Claude가 만든 합성 데이터 60개 질의다. 작성자의 어휘 습관이 질의와 기억에 함께 들어가 어휘 검색에 유리할 수 있다.
* 기억이 50개뿐이라 방해 항목이 적다. 순위 난이도가 실제보다 낮다.
* S7에서 공개 데이터셋(`docs/research.md` §9, `eval/datasets.toml`)과 더 큰 저장소로 다시 측정한다.

**결론:**
* 공개 데이터에서도 2-gram이 기준선보다 R@5 +0.25~0.29 높다.
* kiwi와의 차이는 −0.002~+0.018로 거의 없는데, 색인 생성은 20배 느리다. 그래서 기본 2-gram 결정을 유지한다.
* 혼합 방식은 가장 높지만 차이가 +0.008~0.010이다. 임베딩을 붙이는 S7에서 함께 다시 본다.
* 합성 평가셋과 달리 R@10이 R@5보다 0.03~0.08 높다. 그래서 `search.default_limit`를 5에서 10으로 바꿨다.
* Ko-StrategyQA는 여러 단계 추론 질문이라 어휘 검색의 R@5가 0.62에 그친다. 의미 검색(S7)의 기준선으로 쓴다.

## 2. 커밋 내구성 (`docs/decisions.md` V10)

| 설정 | 기억 300건 추가 p50 | p99 | 최대 |
| :--- | :--- | :--- | :--- |
| `PRAGMA fullfsync=OFF` | 0.087 ms | 0.151 ms | 0.158 ms |
| `PRAGMA fullfsync=ON` | 3.911 ms | 4.257 ms | 4.644 ms |

* macOS의 `fsync`는 드라이브 캐시를 비우지 않는다. `fullfsync`는 `F_FULLFSYNC`로 캐시까지 비운다.
* 켜면 저장이 약 45배 느려지지만 1건당 4 ms다. 기억 저장은 대화 속도로 가끔 일어나므로 체감 비용이 없다고 판단해 기본값을 켬(`storage.fullfsync = true`)으로 정했다.
* 전원 차단 실험은 하지 않았다. 유실 가능성은 SQLite·Apple 문서의 동작 설명에 근거한다 (추정).

## 4. 로컬 모델 교차 세션 기억 (2026-11-21)

재현: `uv run python scripts/local_agent_eval.py`. 설정은 `eval/local_agent.toml`이다.
* 모델: `qwen3.8:27b-mxfp8` (Ollama 0.35.1), `think = false`
* 시나리오: 3개
* 방식: 시나리오마다 세션 A에서 기억시키고, 새 `gonlith serve` 프로세스와 새 대화인 세션 B에서 묻는다.
* 시스템 프롬프트: 서버의 `instructions`
* 판정: A에서 `remember` 성공, B에서 `search` 호출, B 답에 기대 단어 포함

| 회차 | 변경 | 통과 | 도구 호출 | 도구 오류 | 저장 세션 시간 (초) | 질문 세션 시간 (초) | 로컬 토큰 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | 도구 스키마에 허용 값 목록 없음 | 3/3 | 12 | **5** | 31.2(모델 로딩 포함) · 11.0 · 8.3 | 3.6 · 4.1 · 3.8 | 15,996 |
| 2 | `category`·`source`를 설정 목록 기반 enum으로 노출 | 2/3 | 7 | **0** | 10.3 · 6.1 · 5.5 | 3.4 · 4.3 · 4.5 | 10,988 |

* **enum의 효과:**
  * 1회차에는 모델이 `source: "user"`, `category: "health"`·`"project_decision"` 같은 값을 넣어 오류가 났다. 오류 메시지를 보고 다시 시도해서 결국 성공했다.
  * enum을 노출하자 오류가 0건이 되고, 호출 수는 12 → 7, 토큰은 −31%로 줄었다.
  * 서버 쪽 분류 검사는 SDK 스키마 검증과 중복되어 지웠다.
* **2회차 실패 원인 (확인):**
  * 저장문: "User has a peanut allergy (땅콩 알레르기)."
  * 검색어: "피해야 하는 음식 음식 제한"
  * 겹치는 어휘가 없어 어휘 검색이 못 찾았다. 1회차에는 저장문에 "음식…피해야"가 들어 있어서 찾았다.
  * §1의 동의어·한영 교차 오답과 같은 유형이다. 해결은 S7 의미 검색이 맡는다.
* **한계:** 시나리오 3개 × 1회라 모델의 무작위성이 결과에 섞인다. 다음에는 반복 실행해 성공률로 잰다. 저장 언어·재검색을 권하는 안내문 개선도 그때 함께 비교한다.
* 유료 클라이언트 사용량은 0이다. 로컬 모델만 썼다.
