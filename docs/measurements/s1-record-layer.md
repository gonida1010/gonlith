* 기준 루트와 대조하면 로그 변조 7종 모두 검출, 재생만으로는 5/7 검출.
* 미검출 2종(일관된 재작성·꼬리 잘라내기)은 설계대로 S3 서명 승인문과 S4 외부 증인이 맡는다. 일관된 전체 재작성도 같다.
* 정상 로그 오탐 0 (정상 경로 시험 전체 통과).
* **기준선 비교:**
  * 검색 경로에서 검증하지 않는 해시 체인 기억(mnemo)은 자체 문서가 "`recall`이 검증하지 않는다"고 밝힌다 (`docs/research.md` §1).
  * 그래서 내용 변조 4종은 그런 구조에서 읽을 때 드러나지 않는다 (판단, 해당 프로젝트를 우리가 직접 실행해 재현하지는 않음).
  * Gonlith는 4종 모두 읽는 시점에 `broken`으로 막았다 (측정).

## 4. 동시 쓰기 (`docs/decisions.md` V3)

| 프로세스 | 프로세스당 추가 | 유실 | 재생 검증 | 추가 p50 | p99 | 최대 | 실패 프로세스 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 2 | 200 | 0 | 통과 | 0.058 ms | 0.134 ms | 25.8 ms | 0 |
| 8 | 200 | 0 | 통과 | 0.047 ms | 0.177 ms | 142.9 ms | 0 |
| 16 | 200 | 0 | 통과 | 0.046 ms | 0.361 ms | 302.9 ms | 0 |

* V3을 확인했다. `BEGIN IMMEDIATE` 직렬화로 16개 프로세스 동시 쓰기에서도 유실·위치 충돌이 0건이었다.
* 최대 대기 302.9 ms는 `busy_timeout_seconds` 기본값 5.0 s의 약 6%다. 기본값을 유지한다.
* **남은 확인:** p50 0.05 ms는 커밋마다 디스크 동기화가 실제 저장 매체까지 가지 않는다는 뜻으로 보인다 (추정). macOS의 `fsync`는 드라이브 캐시를 비우지 않고, SQLite `PRAGMA fullfsync`가 필요하다는 것이 알려져 있다. 전원 차단 시 마지막 커밋 유실 가능성과 `fullfsync` 비용은 S2에서 측정해 정한다.
